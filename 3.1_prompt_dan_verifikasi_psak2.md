## 3.1a Prompt untuk Gemini Canvas

**Prompt 1 (konstruksi awal)**

```
Buatkan satu file HTML tunggal (HTML + Tailwind CSS via CDN + JavaScript murni) berupa
"Voucher Transaksi Kas Keluar" untuk modul akuntansi. Persyaratan:

1. Header: Tanggal (default hari ini), Nomor Bukti (wajib, unik), Deskripsi Transaksi.
2. Detail jurnal berupa tabel dinamis: kolom Akun (dropdown), Arus Kas
   (Operasi/Investasi/Pendanaan), Debit, Kredit, tombol hapus baris. Tombol "+ Tambah Baris".
   Awalnya 2 baris.
3. Kalkulasi LIVE setiap kali input berubah: Total Debit, Total Kredit, Selisih.
   Hitung dalam sen (integer) agar bebas galat floating point.
4. Indikator keseimbangan: abu-abu bila kosong, HIJAU "SEIMBANG" bila debit = kredit,
   MERAH "TIDAK SEIMBANG: selisih X" bila berbeda.
5. Tombol "Simpan Transaksi" NONAKTIF sampai: debit = kredit dan > 0, minimal 2 baris,
   semua baris punya akun, tidak ada baris debit & kredit sama-sama 0, satu baris hanya
   boleh debit ATAU kredit, header terisi.
6. Aturan kas keluar: minimal satu baris mengkredit akun yang bertanda Kas/Bank.
7. Tampilkan daftar pesan kesalahan validasi di bawah indikator.
8. Saat submit, kirim JSON ke endpoint Supabase RPC (POST /rest/v1/rpc/fn_create_cash_out_voucher)
   dengan parameter p_trx_date, p_ref_no, p_description, p_lines.
9. Format angka Indonesia (1.234.567,00). Desain bersih, responsif, bahasa Indonesia.
```

**Prompt 2 (iterasi)**: "Ambil daftar akun dari GET /rest/v1/chart_of_accounts (kolom account_id, account_code,
account_name, is_cash), dengan daftar akun contoh sebagai cadangan jika gagal. Tampilkan hasil
respons RPC (berhasil/ditolak) di panel bawah form."

**Prompt 3 (iterasi)**: "Tambahkan pesan kesalahan yang spesifik per aturan dan pastikan fungsi submit
memvalidasi ulang sebelum mengirim, karena tombol bisa dimanipulasi lewat DevTools."

## 3.1b NotebookLM: verifikasi kepatuhan terhadap PSAK 2

**Sumber yang diunggah ke NotebookLM**: teks standar PSAK 2 (Laporan Arus Kas) / standar
yang berlaku bagi entitas, plus `voucher_kas_keluar.html` dan `3.2_audit_trail.sql`.

**Prompt untuk NotebookLM**

```
Berdasarkan HANYA sumber yang saya unggah, uji apakah logika kode voucher kas keluar ini
sesuai standar terkait kas dan setara kas. Untuk tiap aturan, sebutkan: (a) ketentuan standar
beserta kutipan paragrafnya, (b) bagaimana kode menerapkannya, (c) sesuai / perlu perbaikan.
Fokus: definisi kas dan setara kas, pengakuan kas keluar, klasifikasi arus kas
(operasi/investasi/pendanaan), penyajian bruto, dan pengendalian pencatatan.
```

**Ringkasan verifikasi (hipotesis kerja; cocokkan dengan keluaran NotebookLM Anda sendiri)**

| Aturan | Penerapan pada kode | Hasil |
|---|---|---|
| Kas = kas di tangan + simpanan bank; setara kas = investasi jangka pendek sangat likuid, mudah dicairkan, risiko perubahan nilai tidak signifikan | Kolom `is_cash` pada akun; voucher wajib mengkredit minimal satu akun `is_cash` | Sesuai. Perlu kehati-hatian memberi tanda `is_cash` pada setara kas (kriteria jatuh tempo singkat) |
| Arus kas keluar dicatat saat pembayaran terjadi | `trx_date` = tanggal pembayaran; nominal = jumlah dibayar | Sesuai |
| Klasifikasi arus kas: operasi, investasi, pendanaan | Awalnya tidak ada field klasifikasi | Perlu perbaikan: ditambah `cash_flow_category` pada `journal_lines` dan dropdown "Arus Kas" di form |
| Arus kas dilaporkan bruto, tidak saling hapus kecuali kondisi khusus | Tiap kas keluar = baris kredit tersendiri | Sesuai |
| Pencatatan berpasangan dan pengendalian internal | Total Debit = Total Kredit, `ref_no` wajib & unik, audit trail (3.2) | Sesuai |

**Kesimpulan**: logika sudah memenuhi pengakuan kas keluar dan pencatatan berpasangan. Perbaikan
yang diusulkan: (1) membatasi akun kredit ke kas/bank/setara kas, (2) menambah klasifikasi arus kas
supaya data siap untuk laporan arus kas. Kedua perbaikan sudah ada di `voucher_kas_keluar.html`
dan `3.2_audit_trail.sql`.
